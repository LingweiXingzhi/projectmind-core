## 2. `code-review` Skill 的两轴结果

### Standards：仓库规范

未发现可证实的 `AGENTS.md`、`TEAM_SOP.md`、`AGENT_STANDARD.md` **硬性违例**。代码没有把 AI 候选写成正式 Project Model；README 对人工图和候选性质有提示。

维护性判断（不是规范违例）：`app.py` 同时放 Git 读取、地图校验、AI 调用和 HTTP 路由；`web/app.js` 同时放布局、绘图、详情和比较。四人并行时这两处是冲突热点。比赛期先指定 A 为公共文件集成人，其余人在独立模块交付；只在实际阻塞时拆分，避免为了形式大重构。

### Spec：用户意图与比赛版建议

1. **较高：地图版本身份缺失。** `app.py:build_snapshot` 用当前地图文件 `load_map(map_path)`，同时用 Git 提交读取代码证据；`compare_commits` 也用当前地图。若地图改动，`Snapshot.revision` 仍只指向代码提交。[Issue #11](https://github.com/LingweiXingzhi/projectmind-core/issues/11) 要求导出“version-pinned graph draft”，当前实现只能证明**代码证据**被固定，不能证明地图本身被固定到同一版本。这项验收只能算**部分实现**。需分别记录地图来源/版本与代码提交，并显示地图是否经过团队核查；在修复前文案必须明确 `revision` 是代码证据版本。
2. **中：AI 解释没有进入交接导出。** `web/app.js:exportDraft` 和 `app.py:export_markdown` 不包含 `ai_candidate` 的观察、可能影响、未知项。若团队用“图 → 变化 → AI → 下一位协同者”做展示，这条链尚未闭合；需把 AI 结果带候选状态和来源安全地纳入交接。
3. **验收缺口：真实 AI 服务未在本机验证。** 现有自动测试替代了网络响应，只证明请求约束与格式处理。比赛前须用团队合法配置的账户做一次真实调用并记录结果；失败时明确原因，不用模拟结果冒充线上表现。

当前未做自动架构生成、正式模型版本治理、真正增量重算，属于长期产品目标和路线建议，README 已说明边界；不作为今天实现 PR 的缺陷。[Issue #17](https://github.com/LingweiXingzhi/projectmind-core/issues/17) 提及“有界 Git 上下文”和“临时图 AI 审查”：现有有界差异只嵌在 `explain_change` 的内部流程；临时图当前只能导出供外部 AI 或人审看，没有应用内 AI 审查入口。[接口约定](../standards/MVP_INTERFACES.md) 已把两者的实际状态说清，不把文档提议写成现有接入点。

## 5. 给四人接入的结论

**已有可读出口，但没有自动接入新模块的出口。** 现有 HTTP JSON 能让独立客户端读取图、证据和比较；现有 Python 函数也可在同一进程调用。B 的 `collect_code_facts`、C 的 `suggest_map`、D 的 `build_handoff` 仍是 `PROPOSED`，代码中不存在；新模块写完后仍由 A 修改 `app.py` / `web/` 接线。若四人都直接改这两处，冲突风险较高；固定一个共同提交、各写独立模块和测试、A 一人接线并每天运行主线，可以把合并冲突缩到接线点。这个流程降低冲突，不等于承诺零冲突。

建议下一个安全顺序：先让团队审查 [协作约定](../standards/COLLABORATION_CONTRACT.md) 和 [接口约定](../standards/MVP_INTERFACES.md)；由 A/B/C/D 按固定样例开工并每日集成；优先补地图版本身份和 AI 交接；在比赛演示前实测外部模型与非作者重放。实际负责人与各 Issue 编号尚未核实，不在本文假填。
