## Coverage and limits

The suite covers triple ACTIVE claims, two equal plus conflicting, chains/cycles/self/broken edges, direct duplicate IDs, multiple scopes, historical mixing, domain authority, empty registries, unavailable/network/timeouts, stale/live metadata, OPEN→CLOSED/MERGED and head changes, main drift/fallback, 5,000 distinct claims and a 5,000-node chain, reorder invariance, nested semantic duplicate JSON object order, bool versus integer distinction, malformed source/type/state/nested values, append integrity, input non-mutation, research-source authority forgery and distinct human confirmation. Neither timestamps nor claim majority choose winners.

Additive output fields are `current_by_scope`, per-current-row `evidence`, `types`, `freshness`, and live/generated provenance. `counts.current` counts scoped current rows, while the compatibility mapping can contain fewer entries. Consumers were notified directly; the pack reviewer owns consumer changes. Invalid-graph conflicts can legitimately contain one claim or equal values and carry `reason="invalid supersedes graph"` with HUMAN_REQUIRED registry problems.

**WITH_LIMITS:** Tests are hermetic with mocked GitHub/network outputs; they do not assert current live PR or GitHub main state. The default main verifier checks the local cached remote-tracking ref and records a check time, not a fetch time. This freshness limit is exposed as `local_reference`; live remote-main publication requires a separate fetch/API capture and source timestamp. Default PR endpoints still target `LingweiXingzhi/projectmind-core` (this extension's current project fixture), so multi-repository deployment requires repository identity binding. Unknown semantic aliases across different claim keys and human prose are not automatically unified. JSON object ordering is normalized, but integer `1` versus floating `1.0` may conservatively conflict. Verifiers are independently called per claim; varying real-world outcomes can legitimately cause a conflict. The guarantees cover identical registry plus identical verifier outcomes, including verification timestamps.

The direct default code_facts verifier removes its previous reliance on a separate head key. Custom verifier dictionaries that register only head keys do not automatically refresh a different code_facts key; callers must supply its direct verifier. Concurrent independent tooling appends are not transactionally locked (the server does not write the registry). These deployment/generalization limits are explicit and not claimed fixed by these test results.
